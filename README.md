# 429 限流熔断与模型自动切换（MaiBot 插件）

检测模型请求返回 **429 Too Many Requests**（限流）后，自动把出问题的模型从它所属
**模型类别（任务）的备选列表**里暂时移除并切换到下一个备选模型，冻结时长可在插件
设置页调整，到期后自动放回原位置。

用来解决这个死循环：

```
请求 → 429 → 等 retry_interval → 重试 → 429 → … → 重试次数耗尽 → 这次请求彻底失败
（下一个请求又从头选中同一个被限流的模型，继续 429）
```

装上插件后：

```
请求 → 429（快照/日志被插件捕获，约 1~3 秒内）
     → 该模型从 [model_task_config.<任务>].model_list 中暂时移除（宿主热重载 < 1 秒）
     → 后续请求直接落到该类别里的下一个备选模型
     → 冻结时间到，模型按原位置插回列表，配置恢复原样
```

## 功能一览

| 能力 | 说明 |
| --- | --- |
| 429 检测 | 双通道：宿主 LLM 失败快照（结构化状态码）+ 应用日志 `app_*.log.jsonl`（兜底） |
| 自动切换 | 把模型从 `model_config.toml` 中对应任务的 `model_list` 移除，宿主热重载后立刻改用下一个备选模型 |
| 暂时冻结 | 默认 180 秒，可在设置页调整；可开启「重复触发时长翻倍」并设上限 |
| 按模型定时长 | **可按模型/任务单独设置冻结时长**（如 5 小时窗口的模型冻 5h、按天限流的冻 1d），规则从上往下先匹配先赢 |
| 到期还原 | 按记录的原位置插回；插件卸载/停用、宿主重启后同样会还原 |
| 冻结范围 | `task`（只冻结出问题的类别，默认）或 `model`（该模型出现的所有类别都移除） |
| 安全护栏 | 剩余模型保底数量、排除任务/模型、演练模式、写前备份、TOML 逐节校验 + 保持 inode 的就地写入 |
| 可观测 | `/429` 命令、LLM 工具、日志、可选聊天流通知；冻结记录持久化在插件数据目录；写入后核对宿主热重载回执 |

## 安装

1. 把插件目录放到 MaiBot 的插件目录下（本机为 `/root/data/MaiMBot/plugins/`）：
   目录名随意，插件身份由 `_manifest.json` 的 `id` 决定（本插件为
   `local.429-model-failover`）。也可以直接在 WebUI → **插件市场**搜索「429」安装
   （插件中心索引的是本仓库的 GitHub Release）。
2. 打开 WebUI → 插件管理 → 找到「429 限流熔断与模型自动切换」→ 启用。
3. 首次加载会在插件目录生成 `config.toml`（**不要手写**，用 WebUI 配置页修改）。

无需额外依赖，只用 Python 标准库 + `maibot_sdk`。

| 冻结时长上限（秒） | 1800 | 翻倍后的上限 |

| 尊重冻结期间的手工改动 | 开 | 冻结期间你改过该任务的 `model_list`（有模型被删掉、且被冻结的模型也没回来）时，到期不再插回去，避免覆盖你的编辑；关掉则一律还原 |
| 按模型自定义冻结时长 | 空 | 规则列表，见下一节 |
| 演练模式 | 关 | 只记录与通知、不改写配置，建议先开一段时间观察 |
| 卸载时还原 | 开 | 插件卸载/停用时立刻还原全部冻结 |
| 外部改动后重新施加冻结 | 开 | 有人在 WebUI 把冻结中的模型放回时，插件会再移除一次 |

### 按模型自定义冻结时长（v1.2.0 起）

不同上游的限流窗口差别很大，用全局的「冻结时长」只能取折中值。这里可以逐条配置
（设置页里是一个可增删的规则列表，每条形如）：

| 字段 | 说明 |
| --- | --- |
| 模型 | 必填（除只填任务的情况），支持 `*` 通配：`Qwen/Qwen3.7-Flash`、`inclusionai/*:free`、`*daily*` |
| 限定任务 | 可选，填 `utils` / `replyer` 等任务名；留空表示所有任务 |
| 冻结时长 | 可读写法：`30m`、`5h`、`1d`、`1d12h`、`90分钟`、`1800`（纯数字=秒） |
| 重复触发翻倍 | `inherit` 跟随全局；`off` 固定为这里的时长（适合按天/按 5 小时限流的模型）；`on` 强制翻倍 |
| 时长上限 / 倍增判定窗口 | 可选，留空跟随全局；写法同上（如 `2d`、`12h`） |
| 备注 | 只给自己看，例如「openrouter 免费档按天限流」 |

**匹配顺序：从上往下，先匹配先赢**，所以把更具体的规则写在前面。都没命中就用全局默认。

示例（按你机器的实际情况填模型名）：

| 模型 | 限定任务 | 冻结时长 | 翻倍 | 判定窗口 | 备注 |
| --- | --- | --- | --- | --- | --- |
| `Qwen/Qwen3.7-Flash` | （空） | `5h` | `off` | （空） | 5 小时窗口，冻满一个窗口再放回 |
| `inclusionai/*:free` | （空） | `1d` | `off` | （空） | 免费档按天限流，冻一天 |
| `poolside/*-free` | `utils` | `2h` | `off` | （空） | 只在 utils 里按 2 小时冻 |
| `stealth/*:free` | （空） | `30m` | `inherit` | `6h` | 短冻 + 翻倍，6 小时内反复被限流才升级 |
| `deepseek-*` | （空） | `10m` | `inherit` | （空） | 只是偶尔挤拥，短冻即可 |

上表的第 3 行演示了「限定任务」，第 4 行演示了「自定义判定窗口」——窗口要设得比冻结时长
长，翻倍才会在连续被限流时持续升级。

判定窗口的副作用要留意：把「倍增判定窗口」设得比冻结时长还短，翻倍就会失效
（放回去的间隔已经超过窗口，计数被重置）——按窗口限流的模型建议配上
`window_duration`（例如时长 `5h` + 窗口 `12h`），这样"放回去立刻又被限流"会继续升级。

规则写错时（时长无法识别、通配符没匹配到任何模型）不会静默忽略：加载与周期体检都会在
日志里给出 `⚠ 以下「按模型冻结规则」没有匹配到任何现有模型` / `⚠ 冻结规则有问题` 告警。

## 工作原理（重要，请读）

MaiBot 目前**没有**对外开放模型调度相关的 Hook 或能力，插件进程也拿不到宿主
的 LLM 调用链，因此本插件走的是「读宿主产物 + 改宿主配置」这条路：

1. **检测**：宿主每次模型尝试失败都会写失败快照
   （`logs/maisaka_prompt/llm_error/<会话>/<时间戳>.json`），里面有
   `request.task_name`、`generation_attempts[].model` 与
   `generation_attempts[].error.status_code`；`llm_models` 记录器也会打日志。
   两条通道都是只读的。
2. **冻结**：把该模型从 `config/model_config.toml` 对应任务的 `model_list` 中
   移除。宿主的 `watchfiles` 监听会在约 1 秒内热重载，`sequential` 策略随即选中
   列表里的下一个模型，`balance` / `random` 也不会再抽到它。
3. **还原**：冻结条目（任务、模型、原位置、到期时间）持久化在
   `data/plugins/<插件id>/state.json`，到期后按原位置插回；插件卸载、宿主重启
   都会先做一次一致化处理，不会留下被永久删掉的模型。

写入安全性：

* 只做外科式文本替换（只替换目标数组字面量区间），文件其余部分逐字节保留；
* 写前用 `tomllib` 解析新旧文本并逐节比对（`models` / `api_providers` / 其他
  任务表有任何非预期差异就中止写入）；
* 先备份到插件数据目录，再**就地写入**（保持 inode 不变）；
* 写完立刻回读复核，不一致则报错并保留备份，宿主热重载后插件还会核对一次；
* `剩余模型保底数量`、`排除的任务/模型` 等护栏防止把列表改空。

> **为什么不用「临时文件 + `os.replace`」的原子替换？**
> 宿主的 `watchfiles` 文件监听是 inotify 挂在 **inode** 上的。实测：用
> `os.replace` 换掉 `model_config.toml` 后，宿主既收不到变更事件、也不会自己
> 恢复（没有任何异常触发监听重启），配置改动会静默失效。所以插件改为一次
> `pwrite` + `ftruncate` 就地覆盖：inode 不变，宿主稳定收到 `Change.modified`
> 并在约 1 秒内热重载。写入体积只有十几 KB，且宿主只在收到变更事件（还带
> 600ms 防抖）后才读文件，不存在读到半截文件的窗口。

已知边界：

* **当前正在重试的那一次请求无法被打断**（宿主没有对外 Hook）。插件会在第一次
  429 出现后约 1~3 秒内完成冻结，因此「被限流的模型继续吃满本次重试次数」这件事
  仍会发生一次，但从下一个请求开始就不会再撞上它。想进一步减少浪费，可以在
  `model_config.toml` 的 `[[api_providers]]` 里调小该供应商的 `max_retry`。
* 只有在 `[model_task_config.<任务>]` 里出现的任务才能被调度；像 `A_Memorix.*`
  这种由其它插件自建的任务名不在模型配置里，插件会记录并跳过（日志级别 debug）。
* 嵌入类任务（`embedding` / `image_embedding`）默认排除：切换嵌入模型会让新旧
  向量不再可比，宁可不熔断。
* **宿主的文件监听可能被别的东西弄失效**：WebUI 保存模型配置、编辑器「原子保存」
  都会换掉 inode，使监听静默失效。插件在每次写入后会等待宿主热重载回执，超时
  （默认 12 秒）就会在日志里给出「建议重启 MaiBot」的告警，`/429状态` 里也会显示
  `宿主热重载确认：⚠ 超时未确认`。

## 运行观察（长期跑下来会看到什么）

* **冻结时长会升到上限并停在那里**：判定「重复触发」的参照点是**最近一次尝试该模型的时间**
  （上次冻结开始与上次还原时间取较晚者）。只要模型一放回去就立刻又 429，时长就按
  `180 → 360 → 720 → 1440 → 上限` 递增并保持在上限；等它真的恢复（判定窗口内不再 429）
  才会回落到初始值。每个「冻结 → 到期还原」周期会写 2 次宿主配置（宿主也就热重载 2 次），
  所以被长期限流的模型大约每半小时一次写入，日志里会看到成对的「已冻结」「已还原」。
* **配置体检**：插件启动后每 10 分钟检查一次模型配置，如果某个任务的 `model_list`
  里引用了**没有在 `[[models]]` 中声明**的模型名，会在日志里给出 `配置体检：…` 告警，
  `/429状态` 里也会列出。这类名字不会产生 429（插件的熔断帮不上忙），但宿主每次调用
  都会直接抛「未找到名为 X 的模型」并让该次请求失败，而且因为错误发生在罚分之前，
  `balance` 策略会反复挑中它——务必补声明或从列表里删掉。
* **冻结期间有人手工改 `model_config.toml`**：分三种情况——
  1. 只是**新增**了别的模型：插件保留新增，并按记录的前驱/后继锚点把冻结的模型插回原位置；
  2. **删掉**了原本存在的模型（且被冻结的模型也没回来）：判定为「你在重做这份列表」，
     到期**不再插回**被冻结的模型，只记一条「未还原」说明（可用「尊重冻结期间的手工改动」关掉）；
  3. 把冻结中的模型**放回**列表：若「外部改动后重新施加冻结」开着，插件会再移除一次。
  想立即收回冻结，用 `/429解冻`。
* **插件日志会出现两份**：这是宿主运行时同时走 IPC 与本地日志造成的（其它插件也一样），
  不是插件重复执行；状态文件里的计数器才是准的。

## 数据与排障

插件数据目录（宿主侧可见，本机为 `/root/data/MaiMBot-plugin-data/local.429-model-failover/`）：

```
state.json                 冻结记录 + 已处理事件 + 累计统计
backups/model_config_*.toml 每次改写前的宿主模型配置备份
```

排障步骤：

1. `/429` 看插件是否在工作、数据来源是否「可用」、宿主是否确认过热重载；
2. 看宿主日志里插件输出：`grep 429-model-failover logs/app_*.log.jsonl`；
3. 若提示「无法定位宿主 model_config.toml」，到「高级设置」填 `MaiBot 根目录`；
4. 若怀疑改坏了配置，用 `backups/` 里最近一份备份覆盖
   `config/model_config.toml` 即可（宿主机型配置）；
5. 想先观察不改写：打开「演练模式」，插件仍会检测、记录、通知，但不落盘；
6. 手写 `config.toml` 时注意 TOML 语法：规则列表要么整体写成 `model_rules = []`，
   要么整体写成 `[[freeze.model_rules]]` 数组表，**不能两者并存**，否则宿主会打印
   「读取插件配置失败 … Cannot mutate immutable namespace」并继续沿用旧配置（插件不会崩，
   但新配置不生效）；建议一律用 WebUI 设置页维护；
7. 日志/`/429状态` 出现 `配置体检` 告警 = 有任务引用了未声明的模型，按提示补 `[[models]]`
   声明或删掉名字；
8. 日志里出现「写入模型配置后 N 秒仍未收到宿主热重载确认」= 宿主的文件监听失效
   （WebUI 保存配置或编辑器原子保存换掉了 inode），此时插件的改动不会被宿主读到，
   重启一次 MaiBot 即可恢复。

## 自测

不需要 MaiBot 也能跑（只依赖 Python ≥ 3.11 标准库）：

```bash
python3 tests/test_offline.py          # 期望最后一行：全部 37 个测试通过
```

在运行中的容器里复验：

```bash
docker exec -w /MaiMBot/plugins/maibot-429-model-failover maim-bot-core \
    /MaiMBot/.venv/bin/python tests/test_offline.py
```

其中 2 项是**插件级**测试（组件注册、默认配置、热重载确认状态机），需要 `maibot_sdk`；
在没有 SDK 的机器上它们会打印「（跳过：本机没有 maibot_sdk，请在 MaiBot 容器内运行）」
并按通过计入，总数仍是 37。

## 常见问题

**Q：会不会把我 `model_config.toml` 里的注释/格式改乱？**
不会。只替换 `model_list` 的数组字面量区间，其余内容逐字节保留，且自测里有
「移除再还原后与原文件完全一致」的用例。

**Q：插件被卸载时正好有冻结怎么办？**
`on_unload` 会按配置（默认开启）还原全部冻结；即使卸载时还原失败，下次加载
也会根据 `state.json` 再还原一次。

**Q：宿主重启后冻结还在吗？**
在。冻结记录是持久化的，重启后会继续计时；若重启期间已到期，加载时会立刻还原。

**Q：为什么不在 429 发生的那一次请求里直接换模型？**
因为宿主没有对外暴露 LLM 调用链的 Hook，插件只能通过文件级产物感知失败。想彻底
缩短这段窗口，可以把供应商的 `retry_interval` 调小、`max_retry` 调小，让宿主更快
切到下一个模型，本插件则负责让「下一个请求」不再选中被限流的模型。

## 启动期为什么会有一次「未收到热重载回执」提示

MaiBot 启动时，插件可能比宿主的配置热重载广播机制先就绪：这段时间里宿主的配置变更通知会被丢弃，插件写完 `model_config.toml` 后自然收不到回执。插件对此的处理是：

1. 加载后 12 秒内没收到回执 → `WARNING` 写一条「宿主可能仍在启动」，然后**就地重写一次配置**（内容不变）强制触发一轮热重载；
2. 只要还在 180 秒启动宽限期内，就**每 30 秒重写一次**，直到收到宿主确认；期间不会升级成错误；
3. 只有超出宽限期仍无回执，才按「宿主文件监听可能失效」记 `ERROR` 并建议重启 MaiBot。

所以启动日志里看到第一条 `WARNING` 是正常现象；看到 `ERROR 写入模型配置后 N 秒仍未收到宿主热重载确认` 才需要处理。

## 平台、依赖与许可证

* **平台**：宿主为 Linux / macOS / Windows 都可以。其中「保持 inode 的就地写入」在
  Windows 上必须显式用二进制模式打开（1.2.4 起已带 `O_BINARY`）——否则 CRT 的换行转换
  会让 `\n` 变成 `\r\n`，随后的 `ftruncate` 按原字节数截断，把宿主配置写坏。
* **依赖**：无第三方依赖，只用 Python 标准库（需 ≥ 3.11，用到 `tomllib`）与 `maibot_sdk`。
* **数据面**：插件不发起任何网络请求、不上报任何数据；只读宿主的日志与模型配置，
  只写 `model_config.toml` 的 `model_list` 和插件自己的数据目录。
* **许可证**：MIT，见仓库根目录 [LICENSE](./LICENSE)（Copyright © 2026 deepseekv41flash）。
* **发布约定**：`id` 固定为 `local.429-model-failover`，不会变更；每个 GitHub Release
  的 Tag 与 `_manifest.json` 的 `version` 一致（如 Tag `v1.2.4` ↔ `"version": "1.2.4"`）。
